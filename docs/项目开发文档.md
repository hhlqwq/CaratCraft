CaratCraft(克拉匠造)为珍珠商城与项链定制项目. 首期四个入口为商城、DIY、社区、我的, 购物车从商品和个人中心进入. 包含二维材料排列、服务端报价、设计保存、订单与工单、售后、协议及微信云开发AI建议. 三维颈模、AR、自由建模、多商家和跨境支付不属于当前已确认交付范围.

甲方《珍珠信息合集》需求资料于2026-10-15接收, SHA256为`4cdb7d6266146989ee6bac5fbba25069612578aaa3f27ee3456a6b299c9f1c0f`. 其中问句、示意图、行业知识和其他商家身份不作为已确认生产规则或可发布素材. 品牌、工艺、素材及真实经营资料由经营者确认.

## 3. 数据契约

### 3.1 标识与标准变更

`goodsId`表示商品, `productId`表示SKU, `specificationId`表示规格组. 页面所用规格值行ID仅用于定位选项, 不得与规格组ID混淆. 交易以服务端验证过的商品和SKU身份为准.

统一采用重构后台的具名SKU组合: `规格组ID:完整规格值`, 组间用`|`连接, 按规格组ID升序生成. 示例为`7:白色|8:8mm`. 无规格仅使用空字符串, 一个商品仅有一个默认SKU. 每组恰有一项, 值不为空且不含分隔符`|`, 不做子串或忽略大小写的匹配. 组合总长度最多2048个UTF-16编码单元, 组合数量最多512, 由SkuContract常量定义; 前端及数据库同步该限制.

旧数字下划线组合只能通过明确迁移转换为上述格式, 运行时不同时接受两种格式. 迁移无法映射的记录须阻断升级并报告. 历史订单保留已成交时的文字和金额, 不改写历史来伪造新格式记录.

商品编辑时保留未改变组合的SKU身份和库存, 不删除重建整套SKU. 已删除或停用的组合不得被另一个组合复用身份. 新组合创建新身份; 改价不改写历史订单.

### 3.2 金额、数量及尺寸

| 字段/概念 | 唯一含义 |
| --- | --- |
| `number` | 购买件数, 整数1到9999, 合并后仍校验上限和库存 |
| `goodsNumber` | 当前SKU库存, 不能读取SKU数组本身的属性 |
| `retailPrice` | 当前SKU销售单价, 服务端BigDecimal, 客户端仅展示 |
| 实测颈围 | 用户实测值, mm, 不由AI估算覆盖 |
| 目标成品长度 | 商家规则下承诺的目标, mm, 不等同材料跨度 |
| 材料跨度参考 | 二维排列的几何参考, 不作为生产承诺 |
| 工艺成品估算 | 按SUM/OVERLAY_MAX及扣件、连接、缩短量计算, 避免重复计长 |

未知尺寸和工艺参数保持空值, 未满足完整下单条件时可保存草稿但不可下单. 金额使用十进制精度, 时间字段必须明确单位; 现有`addTime`秒时间戳不得被当成毫秒或无时区日期字符串.

### 3.3 HTTP与身份

响应使用`RestResponse<T>`: `success`、`code`、`msg`、`data`、`timestamp`. 成功code为0, timestamp为秒. 401表示会话无效, 403表示权限/归属失败, 428引导确认更新协议; 同时返回相应HTTP状态. 不自动重放被阻断的写操作.

新增和统一后的分页使用page/size请求及records/total/current/size响应, 页大小须有服务端上限. 旧分页接口须先登记调用方后协调迁移, 不让一个接口按客户端种类切换响应结构.

登录、个人资料和公开评价使用白名单DTO. OpenID、IP、运营标签、备注、地址和订单信息不进入公开资料. 账号切换清理全局及本地私人状态, 所有迟到响应核对令牌及页面代次.

## 4. 核心流程

- 商品: 后台维护来源/品类、事实参数、SKU、价格库存及媒体; 保存后小程序组合筛选与详情一致. 未删除且在售并具备必要分类的商品才进入新目录.
- 定制: 四类材料按稳定实例顺序编辑, 服务端累计用量、校验必选和库存、重新报价; 保存更新本人草稿并校验版本. 下单冻结材料、尺寸、工艺、价格及条款版本.
- 交易: 立即购买生成本人独立上下文; 结算和提交再次校验SKU及价格. 下单幂等、库存事务、支付回调和退款对账各有服务端约束. 客户端成功提示不代替服务端支付结果.
- 生产: 审核、制作、质检、发货按状态机流转, 操作和原因可追溯. 不允许通过任意状态文本跳过环节.
- 社区: 设计/成品/建议发布后待审核, 只有公开内容可浏览和点赞. 设计使用公开副本, 不公开私人刻字、身体参数和订单. 不开放评论、私信或好友.
- 协议: 商家发布正式正文, 用户确认当前版本. 新交易冻结版本; 已有订单履约不因新条款被整体阻断. 未发布正文不补造确认记录.
- AI: 明确同意后准备本人一次性票据, 云模型输出经候选、输入绑定和服务端报价复核. 不自动切换收费通道, 不把推荐当作实测或生产规格.

正式V迁移记录不等于多套当前标准. 它们负责已有库升级及校验, 已使用版本不应为减少文件数量而直接合并、删除或修改字节. 后续应统一当前结构目标和执行规则, 清理重复历史副本; 对生成入口明确唯一来源并验证生成一致性. 是否进一步重建空库基线, 需确认方案并验证与已有库升级结果一致, 不能先改再猜测数据结果.

### 8.3 图片与data目录的实际关系

`data/`目前只有`caratcraft-emblem.png`, 尺寸1254×1254, 94,687字节. 小程序实际使用`apps/miniapp/static/images/logo.png`, 尺寸800×800, 53,303字节, 用于登录、分享、默认头像和部分图片占位. 管理端和两个后端还各有favicon.

这些文件由`tools/assets/generate-project-assets.py`的同一几何绘图分支分别生成. 小程序logo并非从`data/`图片缩放取得; 生成器只读取原文件尺寸, 不读取原图片像素派生内容. 因此前文及README将`data/`称为“品牌原始素材”不准确, 当前它不是这些图标的权威设计源文件. 在本次已检索的应用及工具范围内, 该PNG只见于生成器和素材台账, 未发现应用运行时消费.

拟议处理为核对全部引用后删除无实际消费方的`data/`副本, 同步素材台账和交付白名单; 保留有实际打包用途的各端图片, 用唯一生成规则维护. 不应为了“单一标准”把不同尺寸或格式的必要产物全部删除. 后续若收到正式品牌设计源文件, 再确定其唯一权威位置.

### 8.4 环境目录与构建规则

`env/`提供CMD、PowerShell及Bash操作脚本, 调用`deploy/`内唯一的Compose、Dockerfile、Nginx、模板和健康探针. 当前没有两份独立Compose, 两目录分开本身不等于配置冲突; 但从仓库规模和用户诉求看, 可考虑将操作脚本收入`deploy/scripts/`, 只保留一个环境入口目录. 该建议尚未实施.

已经确认的实质差异如下:

- Windows的build和start已分离: 构建使用`--pull --no-cache`, 启动使用`--no-build --pull never`; Bash的start仍默认先构建, `--no-build`只是可选参数.
- Windows按构建输入内容SHA256核对镜像; Bash仍使用Git提交号及dirty标记. 同一份源码在跨平台和无Git交付时没有统一身份规则.
- `tools/delivery/build-jars.sh`直接要求宿主机Maven, `build-admin-ui.sh`直接要求宿主机pnpm, 与客户“只需Docker”的入口并存. 需要明确是否确有独立交付职责, 否则删除或统一调用Docker路径.
- 根Maven POM仍声明旧第三方仓库, `deploy/maven-settings.xml`则将全部仓库镜像到官方Central. 正式脚本传入settings时使用Central, 直接执行Maven时来源不同, 尚未形成统一入口契约.

环境搭建由用户负责. 不恢复此前自动补缓存、搭建验证环境和多轮重跑Maven的做法; 不自动运行构建或启动脚本.

### 8.5 扩展只读审查的新发现与边界

停止前已枚举全部2,222个Git跟踪文件, 检查首层归属、自有文件完全重复组、配置分布、构建和交付入口、规范工具范围, 并回看相关提交历史. 这属于结构和引用层审查, 不表示已逐行审阅全部业务代码.

| 发现 | 当前证据与后续判断 |
| --- | --- |
| Vite工程保留Webpack时期静态启动代码 | `apps/admin-ui/static/config/init.js`仍加载manifest/vendor/app等旧静态包; 当前Vite HTML不引用它, 但构建会复制整个static目录, 会把残留带入产物 |
| 前端配置存在多入口表象 | 当前HTML注入`static/config/index.js`, Vite又将同一文件复制到`config/index.js`; `index-prod.js`也仍保留. 应确认部署和交付消费方后只保留一个有效配置入口 |
| 格式门禁没有覆盖全部自有文件 | 当前格式工具覆盖Java及选定前端/JS工具, 未统一覆盖Python、SQL、YAML、Bash、PowerShell、WXML及管理端static配置; static旧代码仍有2空格和var. 前次“全量格式通过”仅代表既定工具范围通过 |
| 迁移结束后的一次性改写工具仍在当前工具目录 | `tools/maintenance/migrate-admin-slots.cjs`标明“仅用于本次Vue3迁移”, 仍可批量改写源码. 需判断是否删除并交由Git历史保留, 不能将其与持续维护工具混为一谈 |
| 图片别名和重复文件不止品牌图 | 自有素材中有数十个不同名称但字节相同的SVG, 另有若干PNG/WebP完全重复组. 有些可能是不同页面的语义别名或必要应用副本, 不能仅按哈希删除; 需结合生成器、动态菜单及页面引用收敛 |
| 两个后端有公共资源副本 | 两模块application-dev.yml、banner、证书使用说明和favicon有完全相同内容. 应判断哪些可提取共同配置、哪些需要分别打包, 不把合法部署副本误判为两套实现 |
| 部分测试准备工具固定在早期结构 | `tools/database/prepare-integration-database.py`只提取部分旧初始化结构并加首个V迁移, 默认日期也固定在早期. 需核对调用方和测试目的, 避免其被当作当前完整数据库标准 |

已确认文件相同、残留引用或脚本行为差异, 不等于已确认删除安全. 第三方原始许可证据和对应源码未作为自有重复实现清理对象; 不改原始声明或为了去重破坏交付义务. 同样不能凭名称含v1/v2就删除业务模板或历史交易字段.

3. 拟议方向为: 清理SQL历史重复并统一执行来源; 清理无用途data副本并统一素材来源; 收敛环境入口及跨平台语义; 清除Webpack和一次性迁移残留; 补足对应门禁及文档. 不顺带改写未经确认的交易或业务含义.
